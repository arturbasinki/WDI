# Actor · goal

Learner — get a sudoku puzzle they can solve, with the guarantee that it has exactly one
answer, and as many blanks as that allows.

# Main flow (synchronous)

1. Submit a seed; 0 means "use the current time", so a specific puzzle can be reproduced
   ([Sudoku puzzle](/model/sudoku-puzzle.md)).
2. Fill a complete grid by randomized backtracking.
3. Dig cells in random order, restoring any removal that breaks uniqueness
   ([Unique solution](/invariants/sudoku-unique-solution.md));
   see [Sudoku solve workflow](/workflows/sudoku-solve.md) for the shared machinery.
4. Response: the puzzle, its solution, the blank count, cells removed, elapsed time.
5. The client renders one board: generate, enter an own puzzle, check, solve — in the same place.

# Alternative flows

- **Failure to fill a base grid** (a stated internal-error condition) → a server-side error
  response, not a partial puzzle.
- A reproducible seed yields identical output; seeds 1–8 and 42 are the documented cases.

# Honest presentation

Typical result: 55–58 blanks in 1–7 ms. The blurb says "many empty cells (typically 55–58),
guaranteed uniqueness" and never "maximum" — the theoretical ceiling is ~64
([Task catalog consistency](/invariants/task-catalog-consistency.md)).
